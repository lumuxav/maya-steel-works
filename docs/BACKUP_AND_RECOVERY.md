# Maya Steel Works — Encrypted Backup & Recovery

**Applies only to** `lumuxav/maya-steel-works` and Supabase project **`pgaonchvddcnlssigelt`**. **Never connect Universal MGT or another Supabase project.**

## What is implemented

- `maya-encrypted-backup.yml`: manual encrypted database backup and opt-in daily schedule at **22:53 UTC / 01:53 Uganda**.
- `scripts/create-encrypted-maya-backup.sh`: backup using PostgreSQL **17+** `pg_dump`, verify archive index for Maya sales and Supabase Auth users, package manifest with SHA-256, encrypt locally with **age**, upload **only the .age file**.
- `app/backups`: **System Super Admin only**. Provides the GitHub workflow link, optional current artifact status, expiration information, and download/recovery instructions.
- `scripts/verify-encrypted-maya-backup.sh`: offline decrypt, compare SHA-256, and inspect PostgreSQL archive index. This is not a full restore.
- CI: checks backup configuration and runs synthetic encryption/decryption and PostgreSQL restore tests with **no production access**.

**Current provisioning state:** Files alone do **not** mean live backups are running. Until the key/connection configuration below is completed, the automated schedule is **disabled**, and no live Maya backup archive is generated by this feature. **Do not assume protected just because the workflow exists.**

### Retention and costs

- **One encrypted GitHub Actions artifact**, each successful run, retained for **3 days**. It **automatically expires**. It is not a yearly archive.
- Backups fail closed if the encrypted archive exceeds **60 MiB**. This is a conservative Actions-storage safety guard, **not an estimate of future data size**.
- Uses ordinary GitHub-hosted Ubuntu runners and existing private-repository free quotas; GitHub may charge if the repository uses more than the included minutes or storage. Check **Settings → Billing** to ensure no paid overages. Do not enable scheduled backups unless included free resources are sufficient.
- **For year-long safekeeping**, you must regularly download successful .age files and store them **outside GitHub** in two separate safe locations, such as an encrypted external drive and another secure offline location.
- A daily encrypted GitHub artifact does not replace an independent off-site backup.
- **Supabase Storage binary objects are NOT exported**. Only metadata within the database dump is included; profile images or other uploaded objects must be downloaded/exported separately.
- Auth user tables are included if the PostgreSQL user is privileged enough. Identity passwords, provider secrets and Supabase-managed encryption keys can require special restore procedures, credential rotation or fresh login configuration after migration. A dump is **not a one-click full Supabase clone**.

## First-time setup (owned by Maya Super Admin)

### 1. Generate your offline age encryption identity

Install the free [age](https://github.com/FiloSottile/age/releases) command-line utility on a computer **you control**.

In its terminal (PowerShell/Terminal as supported), run:

```bash
age-keygen -o maya-backup-private-key.txt
age-keygen -y maya-backup-private-key.txt
```

The second command prints a **public** `age1...` recipient. Copy the public recipient to GitHub in step 3.

**CRITICAL:** Keep `maya-backup-private-key.txt` **offline**, ideally on two encrypted removable drives in separate physical locations. Without that private key **no one can decrypt your backups**. Never commit, attach, email, paste into ChatGPT, put in a GitHub secret, or upload this private key. If the key is compromised, generate a new keypair and rotate the public recipient; store older keys safely for older archives.

You can share the **public** `age1...` recipient because it cannot decrypt a backup.

### 2. Obtain Maya's database **session-pooler** connection URL

In the **Maya-specific Supabase project**, visit **Connect → Connection string → Session pooler** (not the transaction pooler). Copy the PostgreSQL URI; select port **5432** and ensure **SSL is required**.

The URL includes a password. URL-encode reserved password characters where required. Examples of acceptable *shapes*, not real credentials:

```text
postgresql://postgres.pgaonchvddcnlssigelt:ENCODED_PASSWORD@aws-0-ap-southeast-1.pooler.supabase.com:5432/postgres?sslmode=require
postgresql://postgres:ENCODED_PASSWORD@db.pgaonchvddcnlssigelt.supabase.co:5432/postgres?sslmode=require
```

The first host is **illustrative**; use your exact dashboard-issued session-pooler host/region. The second direct URL may require IPv6 and may not work from GitHub; use session pooler when in doubt.

**Never share the real URI with me in the chat.** Configure it directly in GitHub Actions secrets.

### 3. Add two GitHub settings (Maya repository only)

Go to: [Maya GitHub repository settings](https://github.com/lumuxav/maya-steel-works/settings/secrets/actions)

- **Repository Secrets → New repository secret**: `MAYA_BACKUP_DATABASE_URL` = the **actual Maya PostgreSQL session-pooler URL**.
- **Repository Variables → New repository variable**: `MAYA_BACKUP_AGE_RECIPIENT` = your **public** `age1...` recipient.

The workflow validates the Maya project reference in the host/username and refuses other projects, ports or disabled SSL.

**Never** put the database URI or private decryption key in a GitHub repository variable or in README.

### 4. Run a backup manually first

Open [Maya Encrypted Database Backup](https://github.com/lumuxav/maya-steel-works/actions/workflows/maya-encrypted-backup.yml).

Choose **Run workflow → main**. A successful run must show:

1. Maya-only config validation passed, with no secret values printed.
2. PostgreSQL 17 dumped the authorized database and `pg_restore --list` found expected Auth and sales tables.
3. age encryption completed **before** upload.
4. Exactly one artifact named **`maya-db-encrypted-<run-id>`** appears. Inside is a **`.age` encrypted archive**, never plaintext `.dump`, SQL or Auth exports.
5. Workflow summary says encrypted output was generated.

If any step fails, **the backup is NOT verified**. No archive should be trusted just because a scheduled run started.

### 5. Verify using your offline key

Download the **encrypted** `.age` file to a computer with age and PostgreSQL client installed. **Don't upload the key to GitHub Actions.**

```bash
bash scripts/verify-encrypted-maya-backup.sh /path/to/maya-steel-works-YYYYMMDD.tar.age /path/to/maya-backup-private-key.txt
```

This decrypts into a temporary directory, checks `manifest.json` against the dump, verifies the project reference and lists the PostgreSQL archive contents. Temporary decrypted files are removed on exit.

**This is an integrity check, not a complete restore test.** A real recovery drill requires a disposable, isolated PostgreSQL / Supabase-compatible environment to validate Auth, RLS, sequences, schema and actual data.

For reference, the extracted archive contains:

```text
maya-postgres.dump    PostgreSQL custom-format backup
manifest.json         project, timestamp, revision and SHA-256 integrity record
```

**Do not** run `pg_restore` against live production Maya just to test a backup.

### 6. Opt into daily backups only after success

Repository → **Settings → Secrets and variables → Actions → Variables → New repository variable**:

```text
MAYA_BACKUPS_ENABLED = true
```

The GitHub Actions daily schedule is now eligible to run. A manual run remains available even while the schedule is disabled. The schedule is not guaranteed to execute exactly on time.

**Check daily** that the latest run is green. Failed backup, expired artifact, missing GitHub storage/quota, removed secrets, connection outage, or inability to decrypt means your effective protection may be weaker than it looks.

### 7. Optional: Show last available backup on the Maya Super Admin screen

If you want the app itself to display the newest successful **unexpired GitHub artifact date**, create a **fine-grained GitHub personal access token** scoped **only to the Maya repository**, with **Actions: Read-only** and required metadata access.

Store it in Maya's **Vercel Production environment** as:

```text
MAYA_GITHUB_BACKUP_READ_TOKEN
```

Do not store it in the browser or add `NEXT_PUBLIC_`. Redeploy Vercel after changing environment variables.

When connected, `/backups` queries GitHub's API from a **Super Admin-protected server endpoint** and displays the most recent successful run with a currently unexpired artifact. If not connected it displays **Not independently verified**, with a link to inspect Actions directly.

This is **optional**; the encrypted backup workflow does not require this token. A green GitHub workflow means an encrypted archive was successfully generated and uploaded—not that a full disaster-recovery restore has been certified.

## Secure long-term storage policy

For Maya financial and stock records, establish:

| When | Action | Retain |
| --- | --- | --- |
| Daily | Check the encrypted automated GitHub backup succeeded | GitHub copy expires after 3 days |
| Weekly | Download encrypted `.age`, perform offline integrity check and copy off GitHub | Minimum 4 rolling weekly files offline |
| Monthly | Save a dated encrypted monthly archive in two safe places | At least 12 months |
| Yearly | Preserve one audited year-end archive and recovery evidence | As required by owner/legal/tax retention |
| Quarterly | Practice restoring to a **separate** nonproduction environment | Written evidence of successful recovery |

**Do not wait a year to make the first offline copy.** GitHub Actions artifacts have finite retention and usage quotas.

## Restore: disaster recovery checklist

1. Stop normal business writes. Record the recovery decision and date.
2. Identify the most recent independently stored **encrypted** archive and retrieve your offline private age key.
3. Verify checksum and archive index with the included script.
4. Prepare an isolated Supabase-compatible PostgreSQL instance (possibly a replacement project; do not purchase paid resources without approval).
5. Follow Supabase's official [backup and restore guidance](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore) for roles, extensions, authentication secrets and special schemas.
6. Restore with a compatible `pg_restore` only into the isolated test instance, under an authorized administrator. Restore Storage objects independently from their separate object backups.
7. Validate row counts, foreign keys, sales/inventory/cash calculations, user identities, RLS and privileged RPCs against the original backup. Confirm staff can sign in (or reconfigure Auth/keys where required).
8. Only after documented success, plan a carefully controlled production cutover and update the website connection strings.
9. Audit everything entered manually during the outage; enter it **once** and reconcile actual cash and stock.

**Never delete Maya's source database or overwrite production until a new verified system is working and independently backed up.**

## Failures and safety

| Symptom | Meaning / response |
| --- | --- |
| Missing URL or public age recipient | Backup cannot start. Configure Secret and Variable; do not bypass encryption. |
| URL references another Supabase project | Hard fail. Confirm the correct Maya project reference. |
| SSL disabled or transaction pooler port 6543 | Hard fail. Use an SSL session-pooler URL on port 5432. |
| pg_dump version too old | Upgrade to PostgreSQL 17 client (the workflow installs it). |
| Missing Maya/ Auth table in dump index | Reject incomplete export, inspect DB permissions. |
| Encrypted archive exceeds 60 MiB | Fail closed; arrange a separately reviewed offline secure destination. |
| GitHub artifact expired / Actions quota reached | Download and store externally, inspect usage limits, do not pay without approval. |
| Key lost | Existing age-encrypted archives cannot be recovered. Protect duplicate offline keys. |
| Storage images missing after DB restore | Storage **binaries** require a separate backup and restore; DB dump stores metadata only. |

**The user has explicitly required zero additional cost.** This system is designed around free tools and short retention, but provider plan quotas still apply; running beyond those quotas may not be free. Always verify the GitHub free usage allowance before enabling indefinite scheduled backups.

**Separation rule:** Never use Universal MGT connection strings, data, repo settings or storage as a substitute for Maya's configuration.
